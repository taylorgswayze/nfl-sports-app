# NFL Sports App — Functionality Review & Backfill Plan
2026-07-23 - read-only review; no changes made

## Headline findings

1. **The app is down and cannot start.** The `venv/` directory was deleted
   around June 29 (backend mtime + last log entries agree). Prod tunnel
   nfl.taylorswayze.com returns 530; nothing listens on 8001; the crontab
   entry fails silently every minute because it calls the deleted venv's
   python.
2. **Deployment is the outlier on this host.** Every other app runs as a
   systemd service + a cloudflared service. This one is tmux + Django's dev
   server + a hand-run tunnel: no restart on crash, no boot persistence, no
   alerting — which is why a total outage went unnoticed for ~3.5 weeks.
3. **The database has no scores.** No field anywhere stores a final score,
   game status, or winner. A sports app that cannot show any result.
4. **Two endpoints fabricate data.** `team_stats` and `team_stat_comparison`
   fall back to random number generation (seeded by team id) when a stat is
   missing, and the comparison view mixes real and fake rows in one ranking
   table with no indication in the UI.
5. **Active data corruption.** The Calendar upsert keys on week *name* only,
   so the 2026 rollover rewrote all 23 calendar rows in place: the 285
   games of 2025 now point at "2026" weeks. Playoff games also collide with
   regular-season weeks 1-5 (no season_type on Game), making postseason
   weeks unreachable through the API.

Pipeline: of 7 registered cron jobs, five are empty stubs, one
(UpdateFutureOdds) is implemented but never registered, and the player-stat
refresh is wired to a stub — which is why 2025 player stats froze in
September. Fetchers have a good shared retry session but no per-call error
handling; season/week are computed at import time with two different
day-offset constants, so a long-lived process drifts.

## Backfill assessment (the priority ask)

Good news: the ESPN endpoints already in use are mostly history-capable,
and the two best sources for backfill aren't used yet:

- `.../seasons/{Y}/types/{T}/weeks/{W}/events` — works for any past season.
- Event detail (`cdn.../game?xhr=1&gameId=`) — includes final score and
  status, which the current code fetches and ignores.
- `site.api.espn.com/.../summary?event={id}` — NOT yet used; full boxscore
  (per-player game stats with real stat names), scores, odds — the natural
  source to fill the empty GameStatistic table and to replace `stat_N`
  garbage names.
- Team season stats/records take a season param (code hardcodes current).
- Odds history: closing lines available back to ~2018; line movement is not
  reconstructable — scope odds backfill to closing spread only.

### Prerequisite fixes (must come first)

1. Schema: add `home_score`, `away_score`, `status` (and ideally `winner`)
   to Game; add `season_type_id` to Game; add `season` to StatTeam; re-key
   Calendar unique on (season, season_type, week_num) and repoint Game.week.
2. Idempotency: `get_games_from_espn` / `get_teams_from_espn` pass all
   fields as lookup kwargs with no `defaults=` — any changed attribute
   (kickoff moved, TBD resolved) causes an IntegrityError that aborts the
   loop. Convert to `update_or_create(pk, defaults={...})`. SeasonStatistic
   and GameStatistic already have proper unique constraints (safe).
3. Repair current corruption: restore/re-key the 2025 calendar, separate
   playoff games, drop junk Team rows.

### Backfill design

- `backfill_season --season Y [--types 2,3] [--weeks a-b] [--skip-stats]`
  per-season order: calendar -> teams -> games+results (with scores) ->
  closing odds -> team season stats -> per-game boxscores (fills
  GameStatistic + real stat names + implicit historical rosters).
- `backfill_range --from 2020 --to 2024` runs seasons oldest-first.
- Volume: ~1,000-1,200 requests/season; at a polite 2-4 req/s with the
  existing retry adapter, ~5-10 min per season. Sleep ~0.3s between event
  calls; honor 429s via the existing Retry config.
- Expected rows/season: ~285 games, ~285 outcomes, ~25-30k season stats,
  ~9k team stats, and 150-200k GameStatistic rows if every boxscore line is
  stored (restricting to skill positions + kickers cuts ~70%). SQLite
  handles 5 seasons comfortably (a few hundred MB).
- Current-season freshness then becomes: hourly slate/odds job + a real
  (non-stub) player-stats job using the boxscore of completed events, with
  the gamelog path fixed to pass `?season=`.

## Ranked recommendations

Reliability
1. (S, critical) Rebuild venv from requirements.txt — app cannot start.
2. (M, critical) Move to host-standard deploy: gunicorn/uvicorn behind
   `nfl.service` + `cloudflared-nfl.service`. Retire tmux/runserver.
3. (S, high) Fix crontab to the new venv; delete the 5 stub cron classes;
   register or remove UpdateFutureOdds; add failure alerting.
4. (S, high) Compute season/week at call time via one shared helper (kill
   the 140- vs 150-day offset drift and the hardcoded 2025).
5. (S, medium) Drop django.db logging to INFO; purge the 254k-row cron log.

Data completeness
6. (M, critical) The schema + idempotency prerequisites above.
7. (M, high) Repair the 2025 calendar / playoff-week corruption.
8. (L, high) Implement backfill_season / backfill_range as designed.

Features
9. (S-M, high) Show final scores and W/L once scores exist — the most
   visible gap in the app.
10. (M, medium) Standings view (computed from records + scores).
11. (S, medium) Drive season dropdowns from the API (currently hardcoded
    2022-2025) and make the backend honor `?season=` (today it's ignored —
    the UI season selector is a no-op).

Code health

    empty/404.
13. (S, medium) Fix TeamStatComparison logo URL bug (uses short_name, not a

    grouping currently collapses many players into "Special Teams").
14. (S, low) Delete dead code and stale artifacts (unrouted views, scratch
